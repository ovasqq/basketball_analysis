# basketball_yandex — калибровка корта и вид сверху

По кадру с неподвижной камеры строим гомографию «кадр ↔ корт (метры)» и
переводим всё, что лежит **на полу**, на вид сверху (схему корта).

| Файл | Что делает |
|---|---|
| `main.py` | CLI |
| `basketball/homography.py` | гомография кадр ↔ корт ↔ вид сверху (OpenCV, RANSAC) |
| `basketball/markings.py` | шаблон разметки FIBA, подсветка разметки на кадре |
| `basketball/paths.py` | пути проекта (калибровка, папки с изображениями) |
| `tools/click_points.py` | протыкивание калибровочных точек на кадре → `calibration.json` |
| `tests/` | быстрые проверки |
| `OCCLUSION.md` | как не рисовать разметку поверх объектов |
| `images/source/` | исходные кадры (в git) |
| `images/output/` | результаты запусков: вид сверху, подсветка (не в git) |

```
pip install -r requirements.txt
pip install -e .     # пакет basketball виден из любого скрипта, правки подхватываются сразу
python main.py --frame images/source/frame.jpg --highlight images/output/frame_lightened.jpg
python tests/test_homography.py
```

Оси корта: X вдоль длины (0..28 м), Y поперёк (0..15 м), начало координат в ближнем
к камере левом углу, Y растёт от камеры.

# Мяч на виде сверху: требования к детектору мяча

Раздел для тех, кто делает детектор/трекер мяча. Здесь описано, что нам нужно
получать на каждый кадр и почему.

## Почему нельзя просто взять центр бокса

Гомография верна только для точек **на полу**. Мяч почти всё время в воздухе,
а из одной камеры не видно, на какой высоте он находится: мяч на высоте 3 м и
точка пола за ним дают один и тот же пиксель.

Оценка по текущей калибровке: камера примерно на высоте 8.6 м над ближней боковой.
Мяч в 3 м над центром корта при наивной проекции центра бокса попадает на
**3 м дальше** от камеры (Y = 10.6 вместо 7.5). Это ошибка на треть ширины корта.

Поэтому положение мяча на виде сверху — это **проекция мяча на пол** `(x, y)`
плюс высота `z`. Чтобы восстановить их, нам нужны:

1. **Нижняя точка мяча, когда он касается пола** (отскок при дриблинге или передаче):
   в этот момент проекция точная.
2. **Видимый диаметр мяча в пикселях.** Размер 7 — 24 см, на нашем кадре это примерно
   от 9 px (дальняя сторона) до 19 px (ближняя сторона). По нему оценивается
   расстояние до камеры. Метод грубый: 1 px ошибки ≈ 5–10 % дальности.
3. **Траектория во времени.** В полёте мяч летит по параболе с известным g, и по
   нескольким кадрам 3D-траектория восстанавливается заметно точнее, чем по размеру.
   Для этого нужны точные моменты времени кадров.
4. **Кто владеет мячом.** Пока мяч в руках, его проекция на пол ≈ ноги игрока, а
   ноги стоят на полу, и для них гомография работает.

## Формат выдачи

JSON Lines: одна строка на **каждый** кадр, в том числе кадры без мяча. По пропуску
строки нельзя понять, был ли кадр обработан.

```json
{"frame": 1532, "t": 51.0667, "image_w": 1920, "image_h": 1080,
 "balls": [
   {"bbox": [955.2, 610.8, 971.0, 627.1], "score": 0.91,
    "center": [963.1, 618.9], "diameter_px": 15.6,
    "occluded": false, "mask": {"size": [1080, 1920], "counts": "…"},
    "state": "air", "holder_id": null}
 ]}
```

### Обязательные поля

| Поле | Описание |
|---|---|
| `frame` | номер кадра в исходном видео, с 0 |
| `t` | время кадра в секундах от начала видео (из таймстемпа контейнера, **не** `frame / fps`: в видео бывают пропущенные кадры и переменный fps) |
| `image_w`, `image_h` | размер кадра, **на котором заданы координаты** (см. «Координаты») |
| `balls` | все кандидаты в кадре, отсортированные по `score`; пустой список, если мяча нет |
| `bbox` | `[x1, y1, x2, y2]` в пикселях, float |
| `score` | уверенность 0..1, **без** отсечки по порогу: порог подберём сами |

### Желательные поля (по убыванию пользы)

| Поле | Зачем |
|---|---|
| `mask` | маска мяча, COCO RLE, в размере кадра. Даёт точный центр и диаметр, когда бокс врёт (размытие, частичное перекрытие). Ещё она нужна, чтобы не рисовать разметку поверх мяча (`OCCLUSION.md`) |
| `center`, `diameter_px` | центр и **видимый диаметр мяча**. Если мяч размыт движением, это эллипс: нужна **малая ось** (большая ось растянута размытием и завышает размер). Если не заполнено, возьмём из маски или бокса |
| `occluded` | мяч частично закрыт (рукой, игроком, кольцом). Тогда бокс уже мяча, и по его диаметру нельзя оценивать расстояние |
| `state` | `"air"` / `"floor"` (кадр касания пола) / `"held"` / `null` (неизвестно). Кадры `"floor"` — самые ценные точки траектории |
| `holder_id` | id трека игрока, владеющего мячом, если есть трекинг игроков |

### Координаты

- Пиксели **исходного кадра**: начало в левом верхнем углу, x вправо, y вниз,
  центр левого верхнего пикселя = (0, 0) (как в OpenCV).
- Если модель работает на уменьшенном кадре, кадре с полями (letterbox, как в YOLO)
  или кропе, **пересчитайте координаты обратно в исходный кадр** перед записью.
  Это самая частая и самая незаметная ошибка: координаты смещаются на несколько
  процентов, и всё выглядит «почти правильно». Мы проверяем, что `image_w/image_h`
  совпадают по пропорциям с калибровкой, но обрезку без полей эта проверка не поймает.
- Кадр **не** исправлять от дисторсии, если об этом не договорились отдельно:
  калибровка сделана по исходным кадрам.

### Требования к качеству

- Мяч мелкий: **9–20 px** в диаметре при 1920 px по ширине. Не уменьшайте вход
  модели так, что мяч станет меньше ~6 px.
- В полёте мяч размыт и бывает почти прозрачным. Recall в полёте важнее, чем на
  мяче в руках: мяч в руках мы восстановим по игроку.
- В кадре может быть несколько мячей (разминка, запасные у столика). Отдавайте
  все, разбираться будем трекингом.
- Пропуск кадра лучше, чем уверенный ложный детект: в физическую модель выброс
  попадает сильнее, чем пропуск.

## Что нужно от нас (а не от детектора)

- **Калибровка камеры.** Для 3D нужна не только гомография, но и фокусное
  расстояние / положение камеры. Сейчас они оцениваются по гомографии грубо.
  Нужны 6+ калибровочных точек, лучше и с высотой (кольцо: 3.05 м).
- **Неподвижная камера** или гомография на каждый кадр (планируется через
  ключевые точки корта, KaliCalib).
- **fps / таймстемпы** исходного видео.

## Что получится на выходе

Одна строка на кадр:

```json
{"frame": 1532, "t": 51.0667, "court_xy_m": [14.0, 7.5], "z_m": 3.0,
 "source": "trajectory", "quality": 0.8}
```

`court_xy_m` — проекция мяча на пол в метрах корта; на виде сверху это пиксель
`image_to_topdown`. `source` — откуда взята оценка: `floor` (касание), `holder`
(по игроку), `trajectory` (парабола), `size` (по диаметру), `none`.

## Открытые вопросы

- Какое видео: разрешение, fps, одна камера или несколько? С двумя и более
  синхронными камерами высота мяча находится триангуляцией, и всё становится
  проще и точнее.
- Есть ли трекинг игроков (для `holder_id`)?
- Онлайн (в реальном времени) или офлайн? Офлайн можно сглаживать траекторию
  с учётом будущих кадров, это заметно точнее.
