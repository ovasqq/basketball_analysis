# basketball_yandex — калибровка корта и вид сверху

По кадру с неподвижной камеры строим гомографию «кадр ↔ корт (метры)» и
переводим всё, что лежит **на полу**, на вид сверху (схему корта).

| Файл | Что делает |
|---|---|
| `main.py` | CLI |
| `basketball/topdown/homography.py` | гомография кадр ↔ корт ↔ вид сверху (OpenCV, RANSAC) |
| `basketball/topdown/markings.py` | шаблон разметки FIBA, подсветка разметки на кадре |
| `basketball/kalicalib/` | сеть KaliCalib: `model.py` (архитектура, копия), `kalicalib.py` (кадр -> гомография) |
| `basketball/court18/` | YOLOv8-pose на 18 точек корта (HoopVision и др.), нужен ultralytics |
| `basketball/court33/` | Roboflow basketball-court-detection-2 на 33 точки, нужен inference |
| `basketball/players/` | детекция игроков (YOLO, COCO person) и пиксель «низа ног», нужен ultralytics |
| `tools/detect_feet.py` | изображения → JSON с точками ног игроков (и метрами корта по калибровке) |
| `video.py` | обработка видео: выпрямление объектива, калибровка, трекинг игроков → jsonl позиций |
| `render_video.py` | видео «кадр + мини-карта» по jsonl от `video.py`, без повторной детекции |
| `basketball/calibrate.py` | выбор способа калибровки корта (общий для `main.py` и `video.py`) |
| `basketball/video/` | чтение видео, выпрямление объектива (`Lens`), отрисовка кадра с мини-картой |
| `tools/sportcenter_calib.py` | калибровки корта для камер датасета SportCenter → `calibrations/` |
| `calibrations/` | калибровки корта для конкретных камер (в git) |
| `configs/` | JSON-конфиги прогонов для всех CLI (`-c configs/…json`) |
| `basketball/config.py` | загрузка параметров CLI из конфига |
| `data/` | датасеты (не в git) |
| `basketball/paths.py` | пути проекта (калибровка, папки с изображениями, веса) |
| `tools/click_points.py` | (`python -m tools.click_points`) протыкивание калибровочных точек на кадре → `calibration.json` |
| `tests/` | быстрые проверки |
| `OCCLUSION.md` | как не рисовать разметку поверх объектов |
| `NETWORKS.md` | архитектуры сетей калибровки, как их обучали, как дообучить |
| `images/source/` | исходные кадры (в git) |
| `images/output/` | результаты запусков: вид сверху, подсветка (не в git) |

Все команды запускаются **из корня проекта**.

## Конфиги

У всех CLI (`main.py`, `video.py`, `tools/*`) параметры можно положить в JSON и
передать флагом `-c`. Флаги командной строки переопределяют конфиг:

```
python video.py -c configs/video_ace_4.json
python video.py -c configs/video_ace_4.json --start 45000 --frames 300
```

- ключи — имена флагов (`frames` = `--frames`, `px_per_m` = `--px-per-m`,
  позиционные — по имени: `video`, `images`); ключи на `_` (`_comment`) игнорируются;
- неизвестный ключ — ошибка, опечатка не пройдёт молча;
- относительные пути в конфиге считаются от корня проекта;
- `video.py` пишет итоговые параметры прогона в `<выход>.meta.json`.

Готовые конфиги — в `configs/`. Скрипты в подпапках, которые
импортируют `basketball` (тесты), запускаются через `python -m`.

Окружение одно, на **Python 3.13**: `inference` (court33) пока не ставится на 3.14.

```
uv venv --python 3.13 .venv && source .venv/bin/activate
uv pip install -r requirements.txt
python main.py --frame images/source/frame.jpg --highlight images/output/frame_lightened.jpg
python -m tests.test_homography
python -m tests.test_court_nets
```

## Как строится гомография: `--method`

| `--method` | Откуда точки | Что нужно |
|---|---|---|
| `manual` (по умолчанию) | клики из `calibration.json` (`tools/click_points.py`) | ничего |
| `kalicalib` | KaliCalib, 91 точка сетки по полу | torch, `weights/kalicalib_challenge.pth` |
| `court18` | YOLOv8-pose, 18 точек на линиях разметки | ultralytics, `weights/court18_yolov8_pose.pt` |
| `court33` | Roboflow basketball-court-detection-2, 33 точки | пакет inference, `ROBOFLOW_API_KEY` |

Для любой сети `--frame` обязателен. `--min-score` задаёт порог уверенности точки,
`--thresh` — порог RANSAC, `--weights` — другой файл весов. Каждая сеть
лежит в своей папке и отдаёт одно и то же: `.keypoints(frame)` → (пиксели, метры,
уверенность) и `.homography(frame)` → `CourtHomography`.

У шаблонов сетей из разных проектов оси корта направлены по-разному.
`CourtHomography.from_keypoints` приводит их к нашей конвенции по самому кадру:
+X вправо, +Y от камеры. Поэтому начало координат всегда в ближнем левом углу.

Все три сети обучены на трансляциях NBA или профессиональных лиг. На наших
залах их надо проверять глазами (`--highlight`).

Оси корта: X вдоль длины (0..28 м), Y поперёк (0..15 м), начало координат в ближнем
к камере левом углу, Y растёт от камеры.

## Автокалибровка нейросетью (KaliCalib)

Вместо ручных точек из `calibration.json` их находит сеть
[KaliCalib](https://github.com/CEA-LIST/KaliCalib) (ResNet18 + декодер, MMSports 2022):
91 ключевая точка на сетке по полу корта → та же `CourtHomography` с RANSAC.
Включается флагом `--method kalicalib`.

```
curl -L -o weights/kalicalib_challenge.pth \
  https://github.com/CEA-LIST/KaliCalib/raw/main/models/model_challenge.pth
shasum -a 256 weights/kalicalib_challenge.pth
#   ab2ec59e87fd028740494302f17bcdf2dc0269f6499b4a559fc411f9d507fee7
python main.py --method kalicalib --frame images/source/frame.jpg --highlight images/output/auto.jpg
python -m tests.test_kalicalib
```

Из кода: `KaliCalib(weights).homography(frame)` возвращает `CourtHomography`;
`.keypoints(frame)` — сами точки (пиксели, метры, уверенность).

Что известно на `images/source/frame.jpg` (сеть не дообучалась):
- найдено 80 из 91 точки, RANSAC оставил 55, медиана ошибки по ним ~19 px;
- расхождение с ручной калибровкой 12–45 px (хуже всего у ближней боковой);
- кадр 3:2 растягивается до 960×540 (16:9), как при обучении; сеть обучена
  на других аренах и ракурсах (DeepSport), так что на новых залах проверяйте глазами.

Лицензия KaliCalib — CeCILL 2.1 (GPL-совместимая): для внутренних экспериментов
ограничений нет, но при распространении `basketball/kalicalib/model.py` действуют её условия.
Файл скопирован без изменений из `kalicalib/model_resnet.py` (коммит `3b3f52b`).

## YOLOv8-pose на 18 точек (`court18`)

Это модель из туториала «basketball analysis». Её используют
[HoopVision](https://github.com/Perceptron04/HoopVision),
[HanaFEKI/AI_BasketBall_Analysis_v1](https://github.com/HanaFEKI/AI_BasketBall_Analysis_v1) и
[nba-vision](https://github.com/j7yn/nba-vision). Модель отдаёт 18 точек: углы,
края трапеций, концы средней линии и точки трёхочковой у лицевых. Шаблон в метрах
взят из их `TacticalViewConverter`, он ближе к разметке NBA, чем FIBA.

Веса — из первоисточника, туториала
[abdullahtarek/basketball_analysis](https://github.com/abdullahtarek/basketball_analysis),
с которого скопированы HoopVision, HanaFEKI и nba-vision (раздел «Training the Models»
в его README). Это YOLOv8x-pose, `kpt_shape [18, 3]`, файл 418 МБ:

```
uvx gdown 1nGoG-pUkSg4bWAUIeQ8aN6n7O1fOkXU0 -O weights/court18_yolov8_pose.pt
shasum -a 256 weights/court18_yolov8_pose.pt
#   f6263105e5c2338fafcfd5a6fefd7d1d441e87364635e918dfdbb849f2df1377
```

Pickle внутри проверен статически: импортирует только классы torch и ultralytics.
`Court18` при загрузке проверяет, что это pose-модель на 18 точек.
Можно и обучить самому: `training_notebooks/basketball_court_keypoint_training.ipynb`
из HoopVision на датасете Roboflow `reloc2-den7l`.

Что известно на `images/source/frame.jpg`: **не годится**. Корт найден (бокс 0.95),
но уверенные точки (0.56–0.98) все в полосе x ≈ 630–770 px, то есть в левой трети
корта. Сеть подписывает их как углы лицевой и концы средней линии. С порогом 0.5
остаётся 6 точек и 4 инлайера: гомография проходит через них точно (отсюда
«медиана 0 px»), но расхождение с ручной калибровкой в углах корта — до 1300 px.
Похоже, что как и court33: обучена на трансляциях NBA с половиной площадки, а не на
виде сверху на весь корт.

**Осторожно:** `.pt` — это pickle, при загрузке ultralytics исполняет код из файла.
Берите веса только из доверенного источника. Лицензия ultralytics — AGPL-3.0.

```
python main.py --method court18 --frame images/source/frame.jpg --highlight images/output/court18.jpg
```

## Roboflow, 33 точки (`court33`)

Модель `basketball-court-detection-2/14` используют
[roboflow/sports](https://github.com/roboflow/sports) (ветка `feat/basketball`),
[cs25m116/…Identification](https://github.com/cs25m116/Basketball-Player-Detection-Tracking-Identification) и
[nba_3d_scene_reconstruction](https://github.com/elijahzhao24/nba_3d_scene_reconstruction).
Она отдаёт 33 вершины разметки из `sports/basketball/config.py`. Шаблон считается
по размерам FIBA. Точки 6 и 26 («под кольцом», на кадре это скорее само кольцо в
воздухе) в гомографию не идут.

Пакет `inference` по API-ключу скачивает веса (ONNX) и дальше считает локально.
Ключ: аккаунт на app.roboflow.com → Settings → API Keys → Private API Key
(модель публичная, подходит ключ любого аккаунта).

```
export ROBOFLOW_API_KEY=...
MODEL_CACHE_DIR=weights/roboflow python main.py --method court33 \
    --frame images/source/frame.jpg --highlight images/output/court33.jpg
```

Что известно на `images/source/frame.jpg`: **не годится**. Шаблон точек верный:
трапеция и углы левой половины совпадают с ручной калибровкой с точностью до
отражения Y, которое `from_keypoints` исправляет. Но сеть уверенно (0.96–0.99)
ставит точки средней линии на правую трёхочковую, примерно на 19–21 м вместо 14,
и согласованно «сжимает» корт. RANSAC берёт эту ложную версию, а остальные
уверенные точки все в левой трети кадра и правую половину не задают. Расхождение
с ручной калибровкой — сотни пикселей. Скорее всего, сказывается обучение на
трансляциях NBA, где в кадре обычно половина площадки.

При первом запуске веса скачиваются в `MODEL_CACHE_DIR` (по умолчанию `/tmp/cache`),
дальше берутся оттуда. При импорте `inference` сыплет предупреждениями про
необязательные модели (SAM, YoloWorld и т.п.), на court33 они не влияют.

Не перенесены: у [sportcal](https://github.com/oscardiaz1331/sportcal) (AGPL) и
[CourtVision](https://github.com/moorexavierb/CourtVision) веса не опубликованы, обе
предлагают обучить модель самостоятельно.

## Обработка видео: игроки на схеме корта

`video.py` для неподвижной камеры: каждый кадр выпрямляется по калибровке объектива,
корт калибруется один раз, игроки детектируются и трекаются (YOLO11s + ByteTrack),
точка ног переводится в метры корта.

На выходе:
- `images/output/<видео>.jsonl` — строка на **каждый** кадр:
  `{"frame", "t", "image_w", "image_h", "players": [{"id", "bbox", "score", "foot_px", "court_m", "flags"}]}`.
  Флаги: `cut` — бокс касается нижнего края (ноги обрезаны), `off_court` — точка дальше
  2 м от корта. Таким точкам не верить.
- `<видео>.meta.json` — откуда что взято (видео, объектив, способ калибровки, H).
- видео строит отдельно `render_video.py` по jsonl и meta.json: слева кадр с
  разметкой и игроками, справа мини-карта с хвостами траекторий.

### Датасет SportCenter (EPFL)

Любительский матч, 8 неподвижных синхронных камер, 37 мин, 30 к/с
([страница](https://www.epfl.ch/labs/cvlab/data/sportcenter-dataset/), бесплатно для
исследований, просят ссылаться). Архив 6 ГБ распакован в `data/sportcenter/`.

У камер сильная дисторсия (k1 ≈ −0.35), без выпрямления гомография не работает.
Калибровка корта получается из калибровки камер датасета (`tools/sportcenter_calib.py`),
KaliCalib на этом зале промахивается. Корт в зале нестандартный, 24.5 × 13.1 м
(посчитано по разметке, подробнее — в docstring скрипта).

```
python -m tools.sportcenter_calib --all          # calibrations/sportcenter_ace_*.json
python video.py -c configs/video_ace_4.json      # -> images/output/ace_4.jsonl (+ .meta.json)
python render_video.py -c configs/render_ace_4.json   # -> images/output/ace_4.mp4
```

Скорость на этом Mac (MPS): `video.py` ~50–60 мс/кадр (~1.5–2 мин на минуту видео),
`render_video.py` — несколько секунд на 30 с видео.

## Игроки: точка ног

Игрок переводится на корт по **низу ног**, то есть по середине нижней стороны бокса.
Это точка на полу, а для точек на полу гомография верна. Детектор — официальный
YOLO11s от ultralytics (COCO, класс person), трекинг — встроенный ByteTrack.

```
curl -L -o weights/yolo11s.pt https://github.com/ultralytics/assets/releases/download/v8.3.0/yolo11s.pt
#   sha256 85a76fe86dd8afe384648546b56a7a78580c7cb7b404fc595f97969322d502d5
python -m tools.detect_feet кадр.jpg --calibration calibration.json --draw images/output/feet
```

Ошибки метода: в прыжке точка уезжает от камеры; если ноги закрыты другим
игроком, бокс обрезан снизу и точка смещается к камере.

# Мяч на виде сверху: требования к детектору мяча

Раздел для тех, кто делает детектор/трекер мяча. Здесь описано, что нам нужно
получать на каждый кадр и почему.

## Почему нельзя просто взять центр бокса

Гомография верна только для точек **на полу**. Мяч почти всё время в воздухе,
а из одной камеры не видно, на какой высоте он находится: мяч на высоте 3 м и
точка пола за ним дают один и тот же пиксель.

Оценка по текущей калибровке: камера примерно на высоте 8.6 м над ближней боковой.
Мяч в 3 м над центром корта при наивной проекции центра бокса попадает на
**3 м дальше** от камеры (Y = 10.6 вместо 7.5). Это ошибка на треть ширины корта.

Поэтому положение мяча на виде сверху — это **проекция мяча на пол** `(x, y)`
плюс высота `z`. Чтобы восстановить их, нам нужны:

1. **Нижняя точка мяча, когда он касается пола** (отскок при дриблинге или передаче):
   в этот момент проекция точная.
2. **Видимый диаметр мяча в пикселях.** Размер 7 — 24 см, на нашем кадре это примерно
   от 9 px (дальняя сторона) до 19 px (ближняя сторона). По нему оценивается
   расстояние до камеры. Метод грубый: 1 px ошибки ≈ 5–10 % дальности.
3. **Траектория во времени.** В полёте мяч летит по параболе с известным g, и по
   нескольким кадрам 3D-траектория восстанавливается заметно точнее, чем по размеру.
   Для этого нужны точные моменты времени кадров.
4. **Кто владеет мячом.** Пока мяч в руках, его проекция на пол ≈ ноги игрока, а
   ноги стоят на полу, и для них гомография работает.

## Формат выдачи

JSON Lines: одна строка на **каждый** кадр, в том числе кадры без мяча. По пропуску
строки нельзя понять, был ли кадр обработан.

```json
{"frame": 1532, "t": 51.0667, "image_w": 1920, "image_h": 1080,
 "balls": [
   {"bbox": [955.2, 610.8, 971.0, 627.1], "score": 0.91,
    "center": [963.1, 618.9], "diameter_px": 15.6,
    "occluded": false, "mask": {"size": [1080, 1920], "counts": "…"},
    "state": "air", "holder_id": null}
 ]}
```

### Обязательные поля

| Поле | Описание |
|---|---|
| `frame` | номер кадра в исходном видео, с 0 |
| `t` | время кадра в секундах от начала видео (из таймстемпа контейнера, **не** `frame / fps`: в видео бывают пропущенные кадры и переменный fps) |
| `image_w`, `image_h` | размер кадра, **на котором заданы координаты** (см. «Координаты») |
| `balls` | все кандидаты в кадре, отсортированные по `score`; пустой список, если мяча нет |
| `bbox` | `[x1, y1, x2, y2]` в пикселях, float |
| `score` | уверенность 0..1, **без** отсечки по порогу: порог подберём сами |

### Желательные поля (по убыванию пользы)

| Поле | Зачем |
|---|---|
| `mask` | маска мяча, COCO RLE, в размере кадра. Даёт точный центр и диаметр, когда бокс врёт (размытие, частичное перекрытие). Ещё она нужна, чтобы не рисовать разметку поверх мяча (`OCCLUSION.md`) |
| `center`, `diameter_px` | центр и **видимый диаметр мяча**. Если мяч размыт движением, это эллипс: нужна **малая ось** (большая ось растянута размытием и завышает размер). Если не заполнено, возьмём из маски или бокса |
| `occluded` | мяч частично закрыт (рукой, игроком, кольцом). Тогда бокс уже мяча, и по его диаметру нельзя оценивать расстояние |
| `state` | `"air"` / `"floor"` (кадр касания пола) / `"held"` / `null` (неизвестно). Кадры `"floor"` — самые ценные точки траектории |
| `holder_id` | id трека игрока, владеющего мячом, если есть трекинг игроков |

### Координаты

- Пиксели **исходного кадра**: начало в левом верхнем углу, x вправо, y вниз,
  центр левого верхнего пикселя = (0, 0) (как в OpenCV).
- Если модель работает на уменьшенном кадре, кадре с полями (letterbox, как в YOLO)
  или кропе, **пересчитайте координаты обратно в исходный кадр** перед записью.
  Это самая частая и самая незаметная ошибка: координаты смещаются на несколько
  процентов, и всё выглядит «почти правильно». Мы проверяем, что `image_w/image_h`
  совпадают по пропорциям с калибровкой, но обрезку без полей эта проверка не поймает.
- Кадр **не** исправлять от дисторсии, если об этом не договорились отдельно:
  калибровка сделана по исходным кадрам.

### Требования к качеству

- Мяч мелкий: **9–20 px** в диаметре при 1920 px по ширине. Не уменьшайте вход
  модели так, что мяч станет меньше ~6 px.
- В полёте мяч размыт и бывает почти прозрачным. Recall в полёте важнее, чем на
  мяче в руках: мяч в руках мы восстановим по игроку.
- В кадре может быть несколько мячей (разминка, запасные у столика). Отдавайте
  все, разбираться будем трекингом.
- Пропуск кадра лучше, чем уверенный ложный детект: в физическую модель выброс
  попадает сильнее, чем пропуск.

## Что нужно от нас (а не от детектора)

- **Калибровка камеры.** Для 3D нужна не только гомография, но и фокусное
  расстояние / положение камеры. Сейчас они оцениваются по гомографии грубо.
  Нужны 6+ калибровочных точек, лучше и с высотой (кольцо: 3.05 м).
- **Неподвижная камера** или гомография на каждый кадр (планируется через
  ключевые точки корта, `--method`).
- **fps / таймстемпы** исходного видео.

## Что получится на выходе

Одна строка на кадр:

```json
{"frame": 1532, "t": 51.0667, "court_xy_m": [14.0, 7.5], "z_m": 3.0,
 "source": "trajectory", "quality": 0.8}
```

`court_xy_m` — проекция мяча на пол в метрах корта; на виде сверху это пиксель
`image_to_topdown`. `source` — откуда взята оценка: `floor` (касание), `holder`
(по игроку), `trajectory` (парабола), `size` (по диаметру), `none`.

## Открытые вопросы

- Какое видео: разрешение, fps, одна камера или несколько? С двумя и более
  синхронными камерами высота мяча находится триангуляцией, и всё становится
  проще и точнее.
- Есть ли трекинг игроков (для `holder_id`)?
- Онлайн (в реальном времени) или офлайн? Офлайн можно сглаживать траекторию
  с учётом будущих кадров, это заметно точнее.
